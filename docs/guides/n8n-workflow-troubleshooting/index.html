When you receive an exported n8n workflow JSON file, you can often spot structural problems before spending time debugging inside a live instance. A static JSON review cannot prove that the workflow will execute successfully, but it can surface missing nodes, broken credential references, and environment-specific assumptions that would otherwise only fail at runtime.

This guide walks through a practical pre-import review process you can apply to any exported n8n workflow.

1. Confirm the JSON is structurally valid

The file must parse as valid JSON. If the JSON is malformed, n8n cannot import it at all. Open the file in a text editor or paste it into a JSON validator to confirm it parses without errors.

Valid n8n workflow JSON typically contains top-level fields such as name, nodes, connections, and settings, but the exact structure can vary by n8n version and export method. Do not assume a single universal schema.

2. Count and review nodes

Look at the nodes array and count the entries. Compare this against what you expect the workflow to contain. Watch for:

  • Unexpectedly missing nodes that should be part of the flow
  • Nodes with "disabled": true — these will not execute unless re-enabled
  • Unfamiliar or unexpected node types that may not exist in your n8n version

If a critical processing node is missing or disabled, the workflow will silently skip that step.

3. Find the trigger

Every automated workflow needs a trigger node. Common trigger types include:

  • Webhook — receives HTTP requests from external systems
  • Schedule / Cron — runs on a time-based interval
  • App or service triggers — native nodes for platforms like Slack, GitHub, or Google Sheets

No obvious trigger may be intentional for manually executed workflows or sub-workflow designs. Treat a missing trigger as a review point, not proof of an error.

4. Review credential references

Exported workflows reference credentials by ID or name. These references tell you which credential types are needed, but they do not contain the actual secret values.

Before importing, ensure your destination n8n environment has valid credentials configured for every referenced credential type. A missing credential will cause the affected node to fail at runtime.

Security warning: Never publish real passwords, API keys, OAuth secrets, tokens, or customer credentials. If you are sharing a workflow publicly, remove or replace all credential references first.

5. Inspect HTTP Request nodes

HTTP Request nodes are common failure points. Review each one for:

  • Endpoint URLs — are they correct and reachable from your environment?
  • HTTP method — does the method match the API expectation (GET, POST, PUT, DELETE)?
  • Headers, query parameters, and body — are required fields present?
  • Authentication dependencies — does the request rely on a credential or header-based auth?
  • Plain http:// references — these may fail behind HTTPS-only proxies or strict security policies
  • Environment-specific or local URLs — addresses like localhost or private IPs will not work in a different environment

Do not assume an endpoint works merely because it appears in the JSON. The URL may have been valid when the workflow was exported but could be outdated or environment-specific.

6. Review Webhook / Respond to Webhook structure

A webhook-triggered workflow may use different response modes:

  • Waiting for Webhook — the workflow pauses at the trigger until a second request arrives
  • Immediately — the workflow responds right away

If the workflow is expected to return an HTTP response to the caller, a Respond to Webhook node should typically be present. However, not every webhook workflow requires one — some workflows process data asynchronously without sending a direct response. Review the intended response mode against the actual node structure.

7. Review Code / Function nodes

Code nodes (formerly Function nodes) contain custom JavaScript that runs during execution. You can review the code for:

  • Assumptions about input data structure and field names
  • Referenced external libraries or APIs
  • Side effects such as file writes, database calls, or external HTTP requests

Custom JS can cause runtime behavior that is impossible to fully validate from the JSON alone. Never execute embedded code merely to inspect a workflow — review it statically.

8. Review expressions

n8n expressions (using double-curly-brace syntax) reference data from upstream nodes. When reviewing expressions:

  • Check that referenced field names match the expected output of upstream nodes
  • Large numbers of expressions are not inherently a problem — complex workflows naturally use many
  • Expressions depend on runtime context, so some issues will only surface during actual execution

After import, verify that expressions resolve correctly with real data.

9. Check connections

The connections object defines how nodes are linked. Review it for:

  • Disconnected nodes that may be intentional but deserve verification
  • Expected flow between the trigger, processing nodes, and output nodes
  • Nodes that appear in the nodes array but have no incoming or outgoing connections

A disconnected processing node will never execute, even if it is correctly configured.

10. Look for environment-specific assumptions

Workflows often contain assumptions about the environment they were built in. Watch for:

  • localhost or private IP addresses in URLs
  • Webhook base URLs that point to a specific n8n instance
  • Environment-specific API endpoints (staging vs. production)
  • Credential names that may differ between environments
  • References to external systems that may not be accessible from your network

These assumptions are often the root cause of workflows that work for one person but fail for another.

Quick checklist

  • ☐ JSON parses without errors
  • ☐ Expected nodes are present and not unexpectedly disabled
  • ☐ A trigger node exists (or absence is intentional)
  • ☐ All credential types are available in the destination environment
  • ☐ HTTP Request endpoints are correct and reachable
  • ☐ Webhook response mode matches the intended behavior
  • ☐ Code node logic has been reviewed statically
  • ☐ Expression field references look correct
  • ☐ All nodes are properly connected
  • ☐ Environment-specific URLs and assumptions have been identified

When structural checking is not enough

A static JSON review has limits. The following issues can only be identified by running the workflow in a real n8n environment:

  • Credential authentication and token validity
  • Actual API behavior and response formats
  • Runtime expression evaluation with real data
  • Node-version compatibility between export and import environments
  • Full workflow execution flow and error handling
  • External service responses and rate limits

If the structural review looks clean but the workflow still fails after import, the issue is likely runtime-specific and requires testing in a live environment.
